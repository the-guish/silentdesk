# SilentDesk — Data Model

Status: draft · Last updated: 2026-10-23

SilentDesk is a client, not a system of record (core principle 4). Its own data model exists mainly to **link tasks and topics** to items that live in corporate systems.

## Entities

### Topic
A unit of work the user can act on.

| Field       | Type   | Notes                     |
|-------------|--------|---------------------------|
| `id`        | UUID   | Generated by SilentDesk   |
| `title`     | string | From the first source item (an email's subject today) |
| `createdAt` | RFC 3339 |                         |

### Source item
A reference to one item in a corporate system. **Each source item belongs to exactly one topic.** A topic can have many source items, but until grouping exists, every source item gets its own topic.

Gmail message (the only source today):

| Field       | Type     | Notes                                  |
|-------------|----------|----------------------------------------|
| `messageId` | string   | Gmail ID                               |
| `threadId`  | string   | Gmail thread ID, kept for future grouping |
| `topicId`   | UUID     | The topic it belongs to                |
| `direction` | `inbound` \| `outbound` | `outbound` when Gmail labels it `SENT` |
| `from`, `to`, `subject` | string | Header values, as shown in the queue. Inbox syncs keep `subject` only; `from` and `to` are empty. |
| `date`      | RFC 3339 | Gmail's internal date                  |

Slack direct message:

| Field         | Type     | Notes                                       |
|---------------|----------|---------------------------------------------|
| `channelId`   | string   | DM or group DM conversation ID              |
| `ts`          | string   | Slack message timestamp (ID within the conversation) |
| `topicId`     | UUID     | The topic it belongs to                     |
| `direction`   | `inbound` \| `outbound` | `outbound` when the user sent it |
| `author`, `counterpart` | string | Display names; counterpart is "Group DM" for group DMs |
| `permalink`   | URL      | Opens the message in Slack                  |
| `date`        | RFC 3339 | From `ts`                                   |

The Slack message text is not stored; its first 120 characters become the topic title.

Jira issue:

| Field        | Type     | Notes                                           |
|--------------|----------|-------------------------------------------------|
| `issueId`, `key` | string | Jira's ID and key, e.g. `PAY-412`           |
| `topicId`    | UUID     | The topic it belongs to                         |
| `direction`  | `inbound` \| `outbound` | `inbound` when assigned to the user; `outbound` when the user reported it |
| `status`, `project` | string | Status name and project key              |
| `assignee`, `reporter` | string | Display names                         |
| `url`        | URL      | Opens the issue in Jira                         |
| `date`       | RFC 3339 | Last updated                                    |

The issue summary becomes the topic title; descriptions and comments are not fetched.

GitHub pull request:

| Field        | Type     | Notes                                           |
|--------------|----------|-------------------------------------------------|
| `prId`       | number   | GitHub's ID                                     |
| `repo`, `number` | string, number | `owner/name` and the pull request number |
| `topicId`    | UUID     | The topic it belongs to                         |
| `reason`     | `reviewRequested` \| `assigned` \| `authored` | Why it is in the queue |
| `direction`  | `inbound` \| `outbound` | `outbound` when the user opened it   |
| `draft`, `author` | bool, string | Draft flag and author login             |
| `url`        | URL      | Opens the pull request                          |
| `date`       | RFC 3339 | Last updated                                    |

The title becomes the topic title; descriptions, diffs and comments are not fetched.

### Task
Still stored separately in the webview's `localStorage`, unencrypted (see `docs/working-notes/todo.md`). It will move into the vault, and gain links to topics.

## What is stored locally

| Stored (encrypted)                          | Never stored                         |
|---------------------------------------------|--------------------------------------|
| Topics                                      | Email bodies and attachments         |
| Source item references and display headers  | Slack message text (beyond the title)|
|                                             | Jira descriptions and comments       |
|                                             | Pull request descriptions, diffs and comments |
| Connected accounts (Gmail address; Slack user and workspace; Jira user and site; GitHub login and server) | Google access tokens (kept in memory only) |
| Gmail history ID, where the next sync starts | Passwords                            |

Secrets (the vault key, the Gmail refresh token, the Slack credential, the Jira token and the GitHub token) live in the OS credential store: Keychain on macOS, Credential Manager on Windows, Secret Service on Linux. They are never written to disk by SilentDesk.

## The vault

All local data is one JSON document, encrypted as a whole (core principle 1).

- **Location:** `vault.bin` in the app data directory, for example `~/.local/share/com.silentdesk.app/` on Linux.
- **Cipher:** XChaCha20-Poly1305 with a random 256-bit key and a fresh random nonce on every write.
- **Key:** generated on first run and stored in the OS credential store under service `com.silentdesk.app`, account `vault-key`.
- **File format:** `"SDV1"` (4 bytes) ‖ nonce (24 bytes) ‖ ciphertext and tag. The `"SDV1"` prefix is authenticated as associated data.
- **Writes** are atomic (temporary file, then rename). On Unix the file is mode `0600` and the directory `0700`.
- **Missing key:** if the key is gone but the file exists, SilentDesk refuses to open the vault rather than create a new key and overwrite the data.
- **Tampering:** any change to the file makes decryption fail.

## Open questions

- Should the display headers (`from`, `to`, `subject`) be cached at all, or fetched each time? Caching keeps the queue usable offline; not caching stores less.
- How long should topics with no tasks linked be kept?
- Should personal notes (core principle 5) go in the same vault or a separate one?
